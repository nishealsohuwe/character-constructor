# Архитектурные принципы

### Какие принципы являются обязательными?
1. Ядро не знает о конкретных НРИ.

    Система не содержит логики вида “D&D”, “GURPS”, “Pathfinder”.

    Любая игровая система описывается через данные.

2. Доменная модель универсальна

    Все игровые концепты выражаются через минимальный набор сущностей:

    - Character (персонаж)
    - System (игровая система)
    - Content (контент)
    - Rule (правило)
    - Effect (эффект)
    - Condition (условие)

    Без “классов”, “уровней”, “рас” в ядре.

3. Персонаж = результат применения правил

    Персонаж не хранит “готовую структуру системы”.

    Он хранит:

    - базовые данные
    - выбранный контент
    - применённые правила
    - вычисленное состояние (или возможность его пересчёта)

4. Все механики выражаются через данные

    Любое поведение системы должно быть описуемо без изменения кода ядра.

    Если для новой НРИ нужно писать Python-код — архитектура сломана.

5. Детали системы инкапсулированы

    Каждая НРИ существует как набор:

    - контента
    - правил 
    - конфигураций

    но не как кодовая ветка.

### Какие компромиссы допустимы?
1. Упрощённая первая реализация rule engine

    Можно начать с ограниченного набора типов правил.
2. Частичная привязка к D&D и GURPS на MVP

    Первая версия может содержать “адаптеры” под конкретные системы.

    Но:

    - без хардкода в ядре
    - без if system == ...

3. Денормализация ради производительности

    Можно хранить вычисленные значения персонажа.

    Но источник истины всегда правила + контент.

4. Ограниченный UI в MVP

    Интерфейс может быть “не универсальным” на старте.
### Что считается плохой архитектурой?
1. Хардкод игровых систем

   if system == "dnd":
2. Вшивание D&D сущностей в ядро

   - level
   - class
   - race
   - spell slot
3. Разные модели под разные системы

   - DnDCharacter
   - GurpsCharacter
   - PfCharacter
4. Логика правил в коде приложения

    Правила должны быть данными, не кодом.

5. UI как источник бизнес-логики

    Если логика персонажа зависит от интерфейса — архитектура сломана.
### Какие зависимости допустимы?
1. Backend:

   - Django (как web-слой)
   - PostgreSQL
   - Redis (опционально, кеш/вычисления)
   
2. Rule engine:
   
   - должен быть полностью независим от Django
   
3. Нельзя:
   
   - зависеть от UI
   - зависеть от конкретной НРИ
   - зависеть от форматов экспорта

### Какие технологии выбраны и почему?
1. Django

    - быстрый старт
    - удобная работа с данными
    - зрелая экосистема

2. PostgreSQL

   - сложные связи между сущностями
   - JSONB для гибкого контента
   - версионирование данных
   
3. Python rule engine

   - удобен для интерпретации правил
   - гибкая модель вычислений
   - простота расширения
   
4. (опционально позже)

   - Redis (кеш вычислений персонажа)
   - Celery (пересчёт персонажей)
### Что должно оставаться независимым от конкретной НРИ?
1. Модель персонажа

    Не должна содержать:

    - уровень
    - класс
    - раса
    - конкретные характеристики систем
    - 
2. Rule engine

    Не должен знать:

    - D&D
    - GURPS
    - Pathfinder

3. Контент

    Не должен быть привязан к структуре одной системы.

4. UI

    Не должен зависеть от конкретной системы.
    
    UI отображает:
    
    - структуру данных, а не игровые правила
